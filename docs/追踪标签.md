# 追踪标签扫描：怎么加新的厂商 / 设备

页面：**第 11 页「扫描」**（UP/DN 翻到，按 BOOT 扫 8 秒）。
串口命令：`SCAN` / `SCAN <秒>` / `SCANTOP` / `SCANRAW`。

固件只做**被动监听 + 厂商指纹分类**，不连接、不配对、不解析归属。
遇到不认识的设备，它不会丢，而是把**原始广播**存下来（最多 16 条），用 `SCANRAW` 导出。

---

## 一、先看现在能认什么

| 生态 | 判定条件 | 置信度 |
|---|---|---|
| 苹果 Find My（AirTag 等） | Company `0x004C` + 子类型 `0x12` + 长度 `0x19` | 95 |
| 苹果（排除） | 子类型 `0x07`（AirPods 等） | 不当标签 |
| 谷歌 FMDN | Service UUID `0xFEAA`，首字节 `0x40`/`0x41` | 90 |
| DULT（跨平台反跟踪） | Service UUID `0xFCB2` | 90 |
| 三星 SmartTag | Company `0x0075` 或 UUID `0xFD5A` | 50 / 85 |
| Tile | UUID `0xFEED` / `0xFEEC` / `0xFE84` | 80 |
| 华为 | Company `0x027D`（只到厂商级） | 45 |
| 小米 | UUID `0xFE95` 或 Company `0x038F`（只到厂商级） | 35 |

置信度 ≥80 基本可以当"确定是标签"；50–79 只能提示；<50 仅记录。

## 二、发现新设备：三步

### 1. 扫一次，导出原始载荷

```
SCAN 10          # 扫 10 秒
SCANTOP          # 看已识别的（带 vendor/conf/rssi/seen）
SCANRAW          # 看未识别的原始 hex
```

`SCANRAW` 输出示例：

```json
{"ok":true,"count":16,"items":[
  {"rssi":-72,"seen":8,"hex":"02011a020a110aff4c0010051c1cad65ec"},
  {"rssi":-40,"seen":16,"hex":"0b16eefd050300060335ff30"}
]}
```

### 2. 拆 AD 结构

BLE 广播是 `[长度][类型][数据…]` 的串联，长度字节**不含自己**：

```
02 01 1a                      → len=2, type=0x01(Flags),     data=1a
02 0a 11                      → len=2, type=0x0a(TxPower),   data=11
0a ff 4c 00 10 05 1c 1c ad 65 ec
   └ len=0x0a, type=0xff(厂商数据), Company=0x004C(苹果), 子类型=0x10 …
```

关键类型：

| type | 含义 | 用途 |
|---|---|---|
| `0x01` | Flags | 通用 |
| `0x09` | 完整设备名 | 辅助判断 |
| `0x16` | 16-bit Service Data | 谷歌/Tile/小米用这个（头 2 字节是 UUID，小端） |
| `0xff` | 厂商自定义数据 | 头 2 字节是 Company ID（小端） |

### 3. 判断「哪个字节是身份字段」

拿同一台设备扫久一点（比如 `SCAN 30`），对比同一条记录的多次广播：

| 观察 | 结论 |
|---|---|
| 某段**全程不变** | 可能是 ID / 型号 |
| 某段**每次都在变**（高熵） | 是随机数/公钥，别用来做键 |
| 某字节**每 N 秒 +1** | 帧计数器 |
| 你的手机/耳机能稳定命中 | 那就是手机/耳机，别当标签 |

> 小技巧：把设备断电/配对重置后再扫，如果某段变了，那它就是身份字段。

## 三、把新指纹加进固件

改 `components/tracker_scan/tracker_scan.c` 的 `vendor_of_adv()`：

```c
if (type == 0xFF && dlen >= 2) {
    uint16_t cid = (uint16_t)(d[0] | (d[1] << 8));
    if (cid == 0x004C && dlen >= 4) { /* 苹果，已有 */ }
    if (cid == 0x1234) { *conf = 70; return TRK_HUAWEI; }   // ← 新加
}
if (type == 0x16 && dlen >= 2) {
    uint16_t uuid = (uint16_t)(d[0] | (d[1] << 8));
    switch (uuid) {
    case 0xFExx: *conf = 75; return TRK_TILE;              // ← 新加
    }
}
```

然后在 `tracker_scan.h` 的 `trk_vendor_t` 里加枚举、在 `main.c` 的 `trk_name()` 里加中文名，
重新编译烧录即可。**语义不明的厂商先给低置信度、只记录不告警**，等采样够了再提高。

## 四、Company ID 去哪查

- 蓝牙官方分配表：<https://www.bluetooth.com/specifications/assigned-numbers/company-identifiers/>
- 直接搜十六进制值，例如搜 `0x004C` 就是 Apple
- 查不到说明是小厂随机注册，只能靠自己采样

---

## 五、隐私与边界（重要）

- 只**监听**广播：不连接、不配对、不发 SCAN_REQ、不重放
- 不上传任何数据：结果只在本机屏幕上显示，`SCANRAW` 走 USB 串口，不联网
- 无法解析"这个标签是谁的、在哪"：苹果/谷歌的载荷是加密匿名公钥，华为的 FID 要和云端账号绑定
- 用途限**自查是否被跟踪**，不要用于跟踪别人（详见 README 的免责声明）

---

## 六、已知限制

| 限制 | 说明 |
|---|---|
| 首次扫描要等 15 秒 | 蓝牙协议栈是懒加载的，第一次要初始化；之后很快 |
| 扫描和价签共用射频 | 扫描这 8 秒价签会让路；同一次不并发 |
| 只吃 legacy 广播 | 没开 `CONFIG_BT_NIMBLE_EXT_ADV`，BLE5 扩展广播收不到（追踪标签基本都用 legacy） |
| 最多记 64 台 / 16 条原始载荷 | 按需调 `MAX_ENTRIES` / `TRK_RAW_MAX` |

## 七、设备类型（不只是标签）

扫描结果会再分一层类型，页面上先按类型汇总，再按厂商列出：

| 类型 | 判定线索 |
|---|---|
| **标签** | 苹果 `0x0C`? 不是——苹果 `0x12/0x19`（Find My）；谷歌 `0xFEAA`；三星 `0xFD5A`；Tile `0xFEED/FEEC/FE84`；DULT `0xFCB2` |
| **手机** | 苹果 `0x10`（Handoff）/`0x0F`/`0x05`（Nearby）/`0x0C`/`0x0D`（AirDrop）；华为 `0x027D`；小米 `0xFE95`/`0x038F`；三星 `0x0075` |
| **电脑** | 微软 Swift Pair（Company `0x0006`，子类型 `0x03`）：Windows 电脑/鼠标/键盘配对广播 |
| **耳机** | 苹果 `0x07`（AirPods）；谷歌 Fast Pair `0xFE2C` |

> 说明：苹果的 Handoff/Nearby 广播在 iPhone、iPad、Mac 上都会出现，无法进一步区分手机还是电脑，
> 统一归到「手机」。微软 Swift Pair 能明确指电脑/外设。

实测（作者桌边）：

```
上次 2 秒前 共 7 台
用时 10.0 秒 BOOT 重扫
手机 7
苹果 4   华为 1   小米 2
未知 16 台
最活跃
小米 手机 -64 dBm 8 包
苹果 手机 -71 dBm 8 包
华为 手机 -90 dBm 7 包
```

### 手机 vs 电脑怎么判

苹果的 Handoff/Nearby 广播本身分不出手机还是电脑，所以固件用**三层线索**：

| 层 | 规则 | 结果 |
|---|---|---|
| 1. 微软 Swift Pair | Company `0x0006`，子类型 `0x03` | 电脑 |
| 2. 广播设备名 | 含 `DESKTOP-` / `LAPTOP-` / `MacBook` / `ThinkPad` / `Notebook` / `Windows` / `iMac` / `Surface` | 电脑 |
|  | 含 `iPhone` / `iPad` / `Android` / `Redmi` / `HUAWEI` / `OPPO` / `vivo` / `Galaxy` / `Pixel` / `Honor` / `OnePlus` / `realme` | 手机 |
| 3. 苹果 Continuity 子类型 | `0x0D`/`0x0E`（个人热点） | 手机 |
|  | `0x05`（AirDrop）/ `0x09`、`0x0A`（AirPlay） | 电脑（偏 Mac） |

判定顺序：**名字 > 苹果子类型 > 默认**（厂商分支给的默认类型）。
名字优先级最高，因为这是设备自己声明的。

验证用的构造用例（`SCANTEST <hex>` 可复现）：

| 输入 | 结果 |
|---|---|
| `02011a0aff4c0010051c1cad65ec`（苹果 Handoff） | 手机 |
| `0aff4c000d0a01000000000000`（苹果热点） | 手机 |
| `0aff4c00050a01000000000000`（苹果 AirDrop） | 电脑 |
| `04ff06000300`（微软 Swift Pair） | 电脑 conf=60 |
| `0e094445534b544f502d414243313233`（名字 DESKTOP-ABC123） | 电脑 |
| `09094950686f6e653133`（名字 iPhone13） | 手机 |
| `0c094d6163426f6f6b2d50726f`（名字 MacBook-Pro） | 电脑 |
| `0d095265646d69204e6f7465203132`（名字 Redmi Note 12） | 手机 |

> 现实里大部分手机/耳机**不广播名字**（只有进入配对模式才发），所以「电脑」这一栏
> 通常要靠 Windows 的 Swift Pair 或 MacBook 的 AirPlay/AirDrop 才会出现。

### 扫描时屏幕上有什么

按 BOOT 触发后，页面会变成动态过程（每帧刷新）：

```
扫描中      8%  1.6/20 秒
[███░░░░░░░░░░░░░░░░░░░]   ← 进度条 + 前端光斑
已发现 2 台
手机 2
              ▪ ▪ ▪          ← 三个点轮流亮，表示还在跑
被动监听，不连设备
```

- **百分比 / 已过时间 / 总时长**：`SCAN 20` 就显示 `/20 秒`
- **进度条**：实心填到当前位置，前端跟一小段亮色光斑
- **已发现 N 台**：实时累加（每扫到一个新设备就 +1）
- **类型小计**：标签 / 手机 / 电脑 / 耳机，只显示数量非零的
- **三个点**：每 250ms 换一个亮，看着不像卡死

## 八、支持的手机厂商

| 厂商 | 怎么认 |
|---|---|
| 苹果 | Company `0x004C`（子类型区分标签/耳机/手机） |
| 华为 | Company `0x027D`；名字含 HUAWEI / nova |
| 小米 | Company `0x038F` / UUID `0xFE95`；名字含 Redmi / POCO |
| OPPO | 名字含 `OPPO`（**没有可靠的厂商 ID，只能靠名字**） |
| vivo / iQOO | 名字含 `vivo` / `iQOO` |
| 荣耀 | 名字含 `HONOR` |
| realme | 名字含 `realme` |
| 一加 | 名字含 `OnePlus` |
| 魅族 | 名字含 `Meizu` |
| 通用安卓 | 谷歌 Fast Pair（`0xFE2C`）命中但认不出品牌 |
| 三星 / 谷歌 / Tile / DULT | 见前面指纹表 |

> 为什么 OPPO/vivo 只能靠名字：它们的**厂商 ID 没有公开可靠值**
> （网上流传的 `0x02D5` 实际是 OMRON），所以不猜 ID，改用设备自报的名字。
> 代价是：手机不进配对模式、不广播名字时就认不出具体品牌，只能归「未知」。


类型图标由 `tools/gen_type_icons.py` 用 Pillow 画好再二值化生成
（`components/tracker_scan/include/type_icons.h`），不依赖网络或字体：
标签 = 圆角牌 + 孔 + 系绳，手机 = 机身 + 听筒 + home 条，
电脑 = 屏幕 + 底座，耳机 = 头梁 + 两侧罩。

```

        ▪ ▪ ▪
```

> **微软**图标是手绘的四方块（simple-icons 的四格在 20px 下会糊成十字形）。
